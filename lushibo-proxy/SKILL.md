# Lushibo Proxy · 代理与跨境网络架构

代理工程的本质是**在不稳定的链路上做可靠的传输**。三个指标决定一切：连通率、时延、吞吐。所有设计决策都要能回答"它提升了哪个指标、代价是什么"。

## 触发条件

- **加载时机**：用户要设计跨境链路、选代理协议、自建/优化节点、排查连不上/慢/掉线、分析流量特征、批量管理订阅与节点。
- **中文关键词**：翻墙、代理、科学上网、跨境网络、代理协议、链路拓扑、分流规则、中转、落地、前置、抗封锁、自建节点、机场订阅、端口跳跃、证书、回落、主动探测。
- **英文关键词**：proxy、VLESS、XTLS、Vision、Reality、Trojan、Shadowsocks-2022、Hysteria2、TUIC、WireGuard、mKCP、gRPC、uTLS、CDN fronting、BBR、MSS clamping、multiplex、failover、sing-box、Xray。
- **不加载的情况**：目标是**攻防对抗/内网渗透**走 `$lushibo-pentest`；目标是**逆向代理客户端二进制**走 `$lushibo-reverse`；目标是**日志侧的检测与响应**走 `$lushibo-bluesec`。
- **边界**：本 skill 管链路设计与调优；检测侧规则归 bluesec，客户端逆向归 reverse。

## 执行步骤

### 第 1 步：先定义指标与约束

写清四项，缺一项就不要开始选协议：

| 项 | 取值示例 |
|---|---|
| 目标区域与运营商 | 落地美西，用户侧国内三网 |
| 关键指标 | 连通率 ≥99%、P95 时延 ≤180ms、单流 ≥50Mbps |
| 预算 | 每月 ≤10 美元/节点 |
| 约束 | 是否允许 CDN、是否需要 UDP、是否要抗主动探测 |

判断标准：如果用户只说"要快"，必须先追问"相对什么快"——首包时延、吞吐还是稳定性。三者优化手段互相冲突。

### 第 2 步：协议选型（按威胁模型选，不按热度选）

| 协议 | 传输层 | 抗主动探测 | 抗 QoS 限速 | 性能 | 适用 |
|---|---|---|---|---|---|
| VLESS + Reality | TCP/TLS | 强（借用真实站点证书） | 中 | 高 | 无自有域名、需强伪装 |
| VLESS + XTLS-Vision | TCP/TLS | 中 | 中 | 最高（免二次加密） | 自有域名 + 直连 |
| Trojan | TCP/TLS | 中（回落站点） | 中 | 中高 | 有域名，配置简单 |
| Shadowsocks-2022 | TCP/UDP | 弱-中（无 TLS 外观） | 弱 | 高 | 内网/中转链路 |
| Hysteria2 | QUIC/UDP | 中 | 强（UDP 拥塞控制激进） | 高（弱网优势明显） | 高丢包链路 |
| TUIC | QUIC/UDP | 中 | 强 | 高 | 同上，多路复用更好 |
| WireGuard | UDP | 弱（可识别） | 弱 | 最高 | 点对点/隧道内层 |
| mKCP | UDP | 弱 | 中 | 中（耗流量） | 极端丢包环境 |
| gRPC / WS over TLS | TCP/TLS | 中 | 弱 | 中 | 必须过 CDN 时 |

选型决策树：

1. 没有自有域名 → Reality。
2. 有域名 + 追求吞吐 → VLESS + Vision，`flow=xtls-rprx-vision`。
3. 链路丢包 >3% → Hysteria2（UDP 拥塞控制比 TCP 更耐受）。
4. 必须走 CDN → WS 或 gRPC over TLS，CDN 侧只开 443。
5. 内网或已被信任的隧道 → Shadowsocks-2022 或 WireGuard。

### 第 3 步：链路拓扑设计

四种基本拓扑，按用户数增长演进：

| 拓扑 | 结构 | 优点 | 代价 |
|---|---|---|---|
| 直连 | 用户 → 落地 | 时延最低 | 落地 IP 易被封 |
| 单跳中转 | 用户 → 中转 → 落地 | 落地 IP 隐藏，可换落地 | 多一跳时延 |
| 隧道链 | 用户 → 入口 → 隧道 → 出口 → 落地 | 入口抗封，链路可编排 | 配置复杂，排查难 |
| CDN 前置 | 用户 → CDN → 落地 | IP 不暴露 | 仅 TCP，性能损失，CDN 侧有日志 |

拓扑设计三条硬规则：

1. **入口与落地分离**：入口负责抗封锁，落地负责出口 IP。两者角色不要混在一个节点上。
2. **每增加一跳，P95 时延增加 20-60ms**，超过 3 跳用户体验崩塌，除非中转与落地在同一机房。
3. **必须有一条备用路径**，且切换时间 ≤30 秒（脚本自动切换）。

用 Mermaid 画出拓扑，节点标注：位置、协议、端口、角色（入口/中转/落地）。

### 第 4 步：服务端部署（Xray / sing-box 二选一）

标准流程：

1. 选 VPS：优先选落地地区的原生 IP（非广播段），确认是否被标记为数据中心 IP（影响流媒体与风控）。
2. 系统初始化：更新内核（BBR 需要 4.9+，建议 5.15+）、时区、SSH 端口与密钥登录、防火墙只放行必要端口。
3. 安装内核：官方脚本安装 Xray 或 sing-box，用 systemd 托管，开启开机自启。
4. 证书：有域名用 ACME 自动签发与续期（HTTP-01 或 DNS-01）；无域名用 Reality 借用目标站点的证书链。
5. 配置：服务端与客户端配置必须**逐字段对应**（UUID/密码、端口、传输、TLS 参数、SNI、路径）。
6. 验收：本地用客户端连一次，跑通 DNS 解析、TCP、UDP（若启用）三类流量。

配置核对清单（最容易错的 8 处）：UUID 大小写、`flow` 参数只在 TCP+TLS 下有效、WS 的 path 前后斜杠、gRPC 的 serviceName、Reality 的 publicKey 与 shortId 配对、SNI 与服务端证书一致性、端口是否被云厂商安全组放行、时间同步（时间偏差 >90 秒会导致 TLS 失败）。

### 第 5 步：性能调优

| 层面 | 参数 | 建议值 | 说明 |
|---|---|---|---|
| 内核拥塞控制 | 拥塞算法 | bbr + fq | `net.ipv4.tcp_congestion_control=bbr`，`default_qdisc=fq` |
| MTU/MSS | TCP MSS | 1380-1420 | 隧道内层需 clamp，防分片黑洞 |
| 文件描述符 | nofile | 65535 | 高并发必须调 |
| 缓冲 | rmem/wmem max | 16MB | 长肥管道（高带宽高时延）必须 |
| 多路复用 | mux | 并发 8-16，关闭 TCP 快速打开 | 减少握手开销，过高会队头阻塞 |
| 端口跳跃 | Hysteria2 端口范围 | 20000-50000 | 对抗 UDP QoS |
| DNS | 解析方式 | 远端解析 + 分流 | 防 DNS 泄漏与污染 |
| UDP | 是否启用 | 按需 | 游戏/语音需要，会增大被限速概率 |

调优纪律：**一次只改一项，改完跑同一套测速（同一目标、同一时段、3 次取中位数）**。不做对照的调优都是玄学。

### 第 6 步：稳定性与故障切换

- 健康检查：每 30 秒做一次 TCP 握手 + 一次 TLS 握手 + 一次小请求，三项全过才算健康。
- 切换策略：连续 3 次失败标记不可用，切备用；连续 5 次成功恢复主用。
- 订阅管理：节点列表与规则分离，规则用远程规则集，节点用订阅链接，便于批量更新。
- 日志：只保留连接元数据（时间、目标、耗时、流量），不记录内容；日志轮转 7 天。
- 监控指标：连通率、P95 时延、失败率、每节点流量、异常断开次数。

### 第 7 步：流量特征分析与对抗

要分析的特征（用于自评链路是否"看起来正常"）：

| 特征 | 正常 TLS 的样子 | 代理链路易暴露的点 |
|---|---|---|
| 握手 | 完整 ClientHello，含常见扩展与 SNI | 扩展缺失、顺序异常、SNI 与证书不匹配 |
| 指纹 | 主流浏览器 JA3/JA4 | 客户端库默认指纹（Go/Python TLS 栈） |
| 包长分布 | 与应用协议一致 | 固定包长、周期性心跳 |
| 时序 | 请求-响应有间隔 | 恒定间隔心跳、整点重连 |
| 端口 | 443/80/常见高位端口 | 长期固定冷门端口 |
| 主动探测 | 正常站点会返回真实页面 | 探测时返回空响应或异常 RST |

对抗手段（按有效性排序）：uTLS 指纹伪装 → 真实站点回落 → Reality 借用真证书 → 心跳随机化 → 端口分散与轮换。

自评方法：在链路两端抓包（tcpdump 只抓头部），统计包长分布与握手特征，与同区域直连访问同一站点的流量做对比。差异越大越容易被识别。

### 第 8 步：批量节点与订阅

- 命名规范：`地区-角色-协议-序号`（如 `us-la-vless-01`），便于脚本批量操作。
- 批量操作：用同一份模板 + 变量替换生成配置，避免手改多份。
- 订阅生成：把节点列表转成客户端可识别的订阅格式，配置分流的规则集走远程 URL，便于统一更新。
- 变更管理：任何节点变更前先导出当前可用配置作为回滚点。

### 第 9 步：排障顺序（固定顺序，不要跳）

1. 本机网络是否正常（直连访问目标地区站点）。
2. DNS 是否解析正确（是否被污染）。
3. TCP 是否能握手（端口/安全组/防火墙）。
4. TLS 是否能完成（证书、时间同步、SNI）。
5. 协议层是否匹配（UUID/密码/flow/传输参数）。
6. 是否有流量但无响应（路由规则、出口 IP 被限）。
7. 吞吐低但连通正常（拥塞控制、MTU、多路复用、VPS 带宽上限）。

每步给出判定命令与预期输出，不要"重启试试"。

## 验证方式

1. **端到端可用**：按交付的配置清单从零搭一遍，客户端能完成 DNS、TCP、UDP（若声明支持）三类流量，成功率 100%。
2. **指标可测**：连通率、P95 时延、吞吐三项都有实测数据（命令 + 时间 + 次数），且达到第 1 步设定的目标值。
3. **配置逐字段对应**：服务端与客户端配置表的字段逐条比对，无遗漏、无冲突（重点核对 UUID/flow/SNI/path/serviceName）。
4. **调优有对照**：每个调优项都有改动前后的同一测速结果，至少 3 次取中位数；无对照的调优项不计入交付。
5. **故障切换有效**：手动停掉主节点，备用路径在 30 秒内接管，且脚本日志能看到判定过程。
6. **特征自评有数据**：流量特征分析必须基于实际抓包统计（包长分布、握手特征），不能只写结论。
7. **脚本可跑**：`scripts/health_check.py` 的 `--help` 退出码 0，非法参数退出码 2，正常运行输出每个节点的连通率与延迟分位，并对不健康节点返回退出码 1。

```bash
D:\Python\python.exe scripts\health_check.py --nodes nodes.json --rounds 3 --timeout 3
```
