# Lushibo Bluesec · 蓝队与应急响应

防御方的产出只有三种：**能触发的检测、能执行的处置、能复现的时间线**。写不出规则、拿不出证据链的分析不算完成。

## 触发条件

- **加载时机**：用户给出日志、告警、EDR 事件、主机清单、网络设备日志，要求做检测、排查失陷、写规则、加固、出应急报告。
- **中文关键词**：蓝队、事件响应、应急、分诊、日志分析、入侵检测、威胁狩猎、溯源、加固、基线、检测规则、安全运营、告警、失陷、横向、权限提升、账户审计。
- **英文关键词**：blue team、incident response、IR、triage、SIEM、Sigma、Sysmon、auditd、EDR、IOC、TTP、MITRE ATT&CK、timeline、containment、hardening。
- **不加载的情况**：**攻击方视角**打点/渗透走 `$lushibo-pentest`；**样本本体**逆向与家族分析走 `$lushibo-malware`；**规避检测的对抗实现**走 `$lushibo-evasion`。
- **边界**：本 skill 站在检测与响应一侧；不产出攻击载荷。

## 执行步骤

### 第 1 步：确定事件等级与响应时限

| 等级 | 判据 | 首次响应 | 遏制时限 |
|---|---|---|---|
| P0 | 域控/核心数据库失陷、勒索加密中 | 15 分钟 | 30 分钟 |
| P1 | 单台服务器被控、有横向痕迹 | 30 分钟 | 2 小时 |
| P2 | 单终端恶意进程、钓鱼邮件点击 | 2 小时 | 24 小时 |
| P3 | 扫描、暴力破解失败、可疑但未成功 | 24 小时 | 72 小时 |

先定级再动手。定级错误会导致要么过度处置（业务中断），要么错过遏制窗口。

### 第 2 步：日志与数据源盘点

必须先回答"我有哪些数据、覆盖哪些 ATT&CK 战术"，写成表：

| 数据源 | 关键字段 | 覆盖战术 | 保留期 |
|---|---|---|---|
| Windows 安全日志 | 4624/4625/4648/4672/4688/4698/4720/7045 | 凭据、执行、持久化 | ≥90 天 |
| Sysmon | 1/3/7/8/10/11/12/13/22 | 执行、注入、DNS | ≥30 天 |
| Linux auditd | execve、connect、open | 执行、网络 | ≥30 天 |
| auth.log / secure | sshd、sudo、su | 凭据、提权 | ≥90 天 |
| Web 访问日志 | URL、UA、状态码、字节数 | 初始访问、Web 攻击 | ≥30 天 |
| 边界设备 | 五元组、会话、NAT | 命令控制、横向 | ≥30 天 |
| EDR | 进程树、命令行、网络 | 执行、横向、持久化 | ≥30 天 |

缺口处理：如果关键字段缺失（例如 4688 未开启命令行审计），把"开启审计策略"作为第一优先整改项写进交付物。

### 第 3 步：日志分诊（先用脚本，再人工深挖）

用 `scripts/log_triage.py` 做第一遍机械化分诊，它会检出：暴力破解、爆破后成功登录、可疑账号行为、特权命令执行、非工作时段登录、日志缺口。

```bash
D:\Python\python.exe scripts\log_triage.py .\logs\auth.log .\logs\security.jsonl --out-dir .\triage --threshold 5 --window 60 --rules
```

分诊后的处理顺序：P0 告警 → 时间线定位 → 证据固定 → 遏制。不要一边分诊一边清理，会破坏证据。

### 第 4 步：检测规则编写

规则分三层，每层都要写：

1. **原子层（单事件）**：一条日志命中即告警。例：`4688` 命令行含 `-enc` 且父进程为 Office。
2. **关联层（时间窗）**：多条事件在同一窗口内构成模式。例：5 分钟内同源 IP 失败 ≥5 次后成功登录。
3. **行为层（状态机）**：跨主机的序列。例：A 主机创建服务 → B 主机出现相同服务名 → 同账号登录。

规则模板（Sigma 风格，字段名与映射表对齐）：

```yaml
title: 疑似凭据爆破后成功登录
id: BL-002
status: experimental
logsource:
  product: windows
  service: security
detection:
  fail:
    EventID: 4625
  success:
    EventID: 4624
    LogonType: [3, 10]
  timeframe: 10m
  condition: fail | count() by IpAddress > 5 and success by IpAddress
falsepositives:
  - 运维批量巡检脚本
level: high
tags: [attack.credential_access, attack.t1110]
```

每条规则必须写清：数据源、字段映射、时间窗、阈值、误报来源、验证方法。没有误报说明的规则不能上线。

### 第 5 步：应急响应 SOP（五阶段）

**阶段 1 · 准备**：联系人表、工具包（离线取证盘、内存采集器、只读挂载）、授权书模板、隔离手段（网络 ACL / EDR 隔离 / 拔网线）。

**阶段 2 · 识别与取证（顺序不可乱）**
1. 记录系统时间与时区，与外部时间源比对。
2. 内存镜像优先于磁盘（易失性数据优先原则）。
3. 采集易失数据：进程列表与命令行、网络连接、登录会话、计划任务、服务、启动项、最近打开文件。
4. 磁盘取证：镜像或至少导出关键目录（临时目录、启动目录、Web 根目录、日志）。
5. 每个证据记录：采集人、时间、工具、哈希（SHA-256）、存放路径。

**阶段 3 · 遏制**：按影响面从小到大——单进程终止 → 单主机隔离 → 网段隔离 → 账号禁用 → 凭据重置。遏制动作必须记录时间点，否则时间线无法重建。

**阶段 4 · 清除与恢复**：清除前先确认持久化点全部找到（服务、计划任务、启动项、WMI 订阅、SSH 密钥、Web 后门、数据库作业、容器镜像）。恢复顺序：重建 > 清理。被控主机的清理优先重建。

**阶段 5 · 复盘**：24 小时内出初步报告，7 天内出完整报告。必答：怎么进来的、待了多久、动了什么、为什么没早发现、改了哪条规则能早发现。

### 第 6 步：时间线重建（溯源核心）

把所有证据按时间排序，粒度到秒，时区统一（建议全部转 UTC 后标注本地时间）。时间线要素：

| 列 | 说明 |
|---|---|
| 时间（UTC+8） | 事件发生时间 |
| 来源 | 哪台设备/哪个日志 |
| 主体 | 账号、进程、IP |
| 客体 | 目标主机、文件、服务 |
| 动作 | 登录、执行、写入、连接 |
| 证据 | 日志行号或文件哈希 |
| 判定 | 确认 / 疑似 / 待验证 |

判定纪律：只有一条证据支撑的写"疑似"，两条以上独立来源互证才写"确认"。

### 第 7 步：溯源方法

- **账号溯源**：从登录事件反查源 IP 与登录类型（3=网络、10=远程桌面）；对比该账号的历史登录基线（常用时段、常用来源）。
- **进程谱系**：用父进程链定位投递点（Office → cmd → 脚本 → 载荷），注意父进程伪造（PPID spoof）时会出现"父进程已退出"或时间倒挂。
- **横向路径**：按 4624 LogonType 3/10 + 4648 显式凭据 + 服务创建 7045 串起来，画出主机间有向图。
- **外联溯源**：把内网主机的出站连接与边界日志做 NAT 前后关联，定位真实外联目标与时长。
- **持久化溯源**：按"服务/计划任务/启动项/WMI/账号/SSH 密钥/Web 后门"七类逐个核查，每类给核查命令。

### 第 8 步：加固基线

按"能自动化验证"的方式写，每条含：检查命令、合格判据、修复命令、影响。

| 类别 | 检查要点 |
|---|---|
| 账户 | 默认账户禁用、最小权限、密码策略、双因素、定期审计不活跃账户 |
| 认证 | 禁止明文协议、限制 RDP 来源、登录失败锁定 |
| 主机 | 补丁级别、审计策略、PowerShell 脚本块日志、Sysmon 部署 |
| 服务 | 关闭不必要服务与端口、服务账户降权 |
| 网络 | 分段、出站白名单、DNS 出口收敛 |
| 日志 | 集中采集、时钟同步、保留期、完整性保护 |

### 第 9 步：检测有效性验证

规则上线前必须验证：用无害模拟（Atomic Red Team 类测试或自建脚本）触发一次，确认告警产生；再跑一遍正常业务，确认误报率可接受。记录：规则 ID、验证时间、触发方式、告警是否产生、误报数。

## 验证方式

1. **规则能触发**：每条检测规则都用一次无害模拟验证过，记录触发时间与告警 ID；未验证的规则不计入交付。
2. **字段真实存在**：规则引用的每个字段都能在数据源中查到（给出日志样例行）；字段名拼错即不合格。
3. **分诊可复现**：用 `scripts/log_triage.py` 以相同参数重跑，findings.json 的告警条数与报告一致。
4. **时间线可互证**：每条标"确认"的条目至少有两个独立数据源；只有一个来源的必须标"疑似"。
5. **证据完整**：每个证据文件有 SHA-256 与采集时间，且原始文件未被修改（重算哈希一致）。
6. **加固可判定**：每条加固项都有可执行的检查命令与明确判据（如"返回 0 表示合格"），"建议加强"这类表述视为不合格。
7. **闭环**：复盘报告必须回答"改了哪条规则能更早发现"，并给出该规则的 ID 与验证记录。
