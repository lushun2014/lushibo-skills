# Lushibo Code · 代码工程与自动化

工程化的判据是**可验证**：测试能跑、覆盖率有数、性能有基准、重构有回归保护。没有测试的重构叫改代码。

## 触发条件

- **加载时机**：用户要新建工程骨架、重构既有代码、补测试、搭自动化流水线、做性能优化、做代码度量与审查。
- **中文关键词**：代码工程、重构、单元测试、集成测试、覆盖率、自动化流水线、性能优化、工程骨架、脚手架、脚本自动化、代码审查、依赖管理、类型注解、代码度量、复杂度、重复代码。
- **英文关键词**：scaffold、refactor、unit test、pytest、vitest、jest、go test、cargo test、coverage、lint、ruff、eslint、golangci-lint、clippy、profile、benchmark、complexity、dead code。
- **不加载的情况**：只问"CI 工作流/仓库结构/发布流程"走 `$lushibo-github`；只问"运行环境/工具链安装"走 `$lushibo-sysenv`。
- **边界**：本 skill 管**代码与测试本体**，仓库与流水线配置归 github。

## 执行步骤

### 第 1 步：先度量，再决定改什么

```bash
D:\Python\python.exe scripts\project_scaffold.py metrics .\src --json --out metrics.md
```

关注四个信号：**文件行数 >500 的热点文件**、**函数长度 >80 行的长函数**、**圈复杂度近似值 >15 的分支密集函数**、**内容完全相同的重复文件**。

判断标准：优先改"热点 × 高频修改"的文件。只看行数不改动的文件不用管——重构要按修改频率排优先级。

### 第 2 步：新建工程骨架

```bash
D:\Python\python.exe scripts\project_scaffold.py scaffold --lang python --name myproj --ci github --license mit
```

骨架必须包含：源码目录、测试目录（含至少 1 个真实可跑的测试）、依赖与构建配置、静态检查配置、README（含可复制命令）、.gitignore、CI 配置。

骨架验收标准：生成后立即执行测试命令能通过（绿灯），不需要人工补文件。

### 第 3 步：测试策略

| 层级 | 覆盖对象 | 数量占比 | 运行时长 |
|---|---|---|---|
| 单元测试 | 纯函数、算法、解析、状态机 | 70% | <10 秒 |
| 集成测试 | 数据库、文件系统、HTTP 客户端 | 20% | <2 分钟 |
| 端到端/契约 | 关键用户路径、外部接口契约 | 10% | <10 分钟 |

覆盖率纪律：不追求总覆盖率数字，追求**关键路径覆盖**。规则：

1. 分支覆盖优先于行覆盖；核心模块分支覆盖 ≥80%。
2. 每个修过的 bug 必须补一条回归用例，且用例在修复前必须失败（先验证用例有效）。
3. 测试不得依赖执行顺序；不得依赖网络与真实时间（用注入的时钟或冻结时间）。
4. 断言要具体到值，不要只断言"不抛异常"。

测试命名：`test_<被测行为>_<条件>_<预期>`，例：`test_parse_config_missing_key_returns_default`。

### 第 4 步：重构手法

**前置条件（缺一不可）**：有测试覆盖待改区域 → 记录当前行为基线 → 改动保持小步提交。

| 手法 | 适用症状 | 操作 |
|---|---|---|
| 提取函数 | 函数 >80 行或注释分段明显 | 按"做一件事"切分，保留原函数为编排层 |
| 消除重复 | 两处逻辑相似度 >80% | 提取公共函数，参数化差异点 |
| 引入参数对象 | 函数参数 >5 个 | 聚合成结构体/数据类 |
| 依赖倒置 | 难以测试、直接 new 外部依赖 | 抽接口，构造注入 |
| 用多态替换条件 | 长 if/elif 或 switch | 策略表/映射表 + 处理函数 |
| 拆分模块 | 文件 >500 行且职责混杂 | 按变更原因拆分，而不是按类型拆分 |
| 渐进式替换 | 遗留代码无法一次改完 | 新旧并存 + 适配层 + 特性开关，逐块迁移 |
| 消除可变全局状态 | 测试互相污染 | 显式传参或封装为对象 |

重构纪律：**重构与功能变更不要在同一次提交里**。一次提交只做一件事，出问题能二分定位。

### 第 5 步：自动化流水线

固定顺序（快慢分层）：

```
格式化 → 静态检查 → 类型检查 → 单元测试 → 集成测试 → 构建 → 制品
```

各语言最小命令集：

| 语言 | 格式化 | 静态检查 | 类型 | 测试 | 构建 |
|---|---|---|---|---|---|
| Python | ruff format | ruff check | mypy/pyright | pytest | build/hatch |
| Node/TS | prettier | eslint | tsc --noEmit | vitest/jest | tsup/vite |
| Go | gofmt | golangci-lint | 编译期 | go test -race | go build |
| Rust | cargo fmt | clippy -D warnings | 编译期 | cargo test | cargo build --release |

本地必须提供一条命令跑完上述全部（Makefile / justfile / package scripts），否则开发者会绕过。

### 第 6 步：性能优化（先测量）

**四步法**：定义指标 → 建立基准 → 定位瓶颈 → 验证提升。

1. 定义指标：延迟（P50/P95/P99）、吞吐（QPS）、内存峰值、CPU 时间、IO 次数。选一个作为主指标。
2. 建立基准：固定输入、固定环境、跑 ≥5 次取中位数，记录硬件与版本。
3. 定位瓶颈：采样分析（cProfile/py-spy/perf/pprof/Chrome DevTools），**不要凭直觉猜**。看热点函数占比与调用次数。
4. 验证提升：同一基准重跑，主指标提升 ≥20% 才算有效，同时确认没有其他指标劣化。

常见手段与适用场景：

| 手段 | 适用 | 代价 |
|---|---|---|
| 缓存（内存/Redis） | 重复计算、重复查询 | 一致性、内存占用 |
| 批处理 | 大量小请求/小写入 | 延迟上升 |
| 索引与查询优化 | 数据库慢查询 | 写入变慢 |
| 并发/异步 | IO 密集 | 复杂度、调试难 |
| 算法替换 | 复杂度可降 | 需要理解业务 |
| 减少分配/复用缓冲 | 高频路径 | 可读性下降 |
| 连接池 | 频繁建连 | 连接泄漏风险 |

反模式：没测量就加缓存；用 sleep 掩盖竞态；为了微秒级优化牺牲可读性。

### 第 7 步：依赖管理

- 锁定版本：Python 用 requirements 锁定或锁文件；Node 用锁文件；Go 用 go.sum；Rust 用 Cargo.lock。
- 依赖最小化：能用标准库就不加依赖；引入前评估维护活跃度、许可证、体积、传递依赖数量。
- 定期更新：按周期升级，小版本合并批量升，大版本单独升并跑全量测试。
- 安全：CI 里加依赖漏洞扫描；有已知高危漏洞的依赖不允许合并。

### 第 8 步：代码审查

审查顺序（先看影响面，后看细节）：

1. 变更是否解决了声明的问题（对照 issue/需求）。
2. 边界与错误路径是否处理（空值、超时、并发、部分失败）。
3. 是否有测试，测试是否会在回归时失败。
4. 命名与结构是否表达意图。
5. 性能与资源（循环内的 IO、未关闭的资源、N+1 查询）。
6. 安全（注入、路径穿越、密钥硬编码、日志泄漏）。

评审意见要写"为什么"和可执行改法，不要只写"这样不好"。

### 第 9 步：脚本自动化

把重复劳动脚本化时遵守：参数校验 + --help + 幂等 + 失败即退出并给原因 + 不吞异常。参考本 skill 的 `scripts/project_scaffold.py` 的写法（纯标准库、子命令、--dry-run、--json）。

## 验证方式

1. **骨架可跑**：生成后立即执行测试命令通过；执行一次格式化与静态检查无错误。
2. **度量可复现**：重跑 `scripts/project_scaffold.py metrics` 得到相同统计（同一 commit）。
3. **重构有回归保护**：重构前先跑测试记录结果，重构后结果一致；若待改区域无测试，必须先补测试再改。
4. **覆盖率有数**：报告给出关键路径分支覆盖率数值与生成命令，且 ≥80%。
5. **回归用例有效**：修 bug 的用例在修复前能复现失败（附修复前运行输出）。
6. **性能有对照**：主指标优化前后各 ≥5 次取中位数，提升 ≥20%；同时给出内存/CPU 未劣化的证据。
7. **流水线一键**：在干净环境执行"一条命令"能完成全部检查；故意引入一个静态检查错误，该命令必须失败（证明不是空跑）。
8. **依赖可复现**：锁定文件入库，删除本地依赖目录后按锁定文件重装能跑通测试。
